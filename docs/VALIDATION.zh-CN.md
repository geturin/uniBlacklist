# 0.1.0-candidate.2 验证范围

2026-10-08（Asia/Tokyo），沿用现有云环境。云端没有运行原游戏，没有连接真实 Steam 玩家。原生 Windows + 原版游戏新版接口安装和匹配拒绝仍待用户验证。旧 candidate.1 的 Windows 包及资料没有删改。

## 用户提供的原生 Windows 证据

candidate.1 报告显示旧通信安装位1、搜索6次、候选1个、元数据错误0；现代通信安装失败，过滤已停用。由报告可确认原搜索回调和旧组安装执行到上述状态，不能推定现代组的具体失败语义，更不能推定名单已实际拒绝了玩家。完整错误日志尚未具备。

## 本轮完成的检查

固定版本 MinHook 源文件 SHA-256 全部匹配。MinGW-w64 GCC 14，i686-w64-mingw32，静态运行库，PE32 GUI 与 DLL 构建通过；项目 C++ 编译启用 `-Wall -Wextra -Werror`。临时自建控制程序不进入 Git、源码 ZIP 或 Windows 包，按用户要求不发布测试集。

## 仍未验证

- candidate.2 在该用户 Steam 客户端真实 Messages002 表上的接入；新方式是否消除实际失败。
- 同版本挂钩失败后 GUI 重新连接真实目标的诊断映射；变更经编译及逻辑核查，尚未实测原游戏的失败重连。
- 所有匹配模式是否均能在确认界面前拒绝；名单为空不产生拒绝计数。
- 黑名单玩家已进入 Steam 后端房间后槽位释放和搜索恢复的时序。
- 原搜索对象生命周期、快速取消/刷新和其他索引读者的同步。
- 首次通信初始化到最多100毫秒控制周期安装的窗口、场景1的完整对战覆盖。
- 与 uniGGPO 等同时注入的兼容性；槽位 CAS 冲突和归属检查不能代替多插件实测。
- 本机权限和安全软件对页保护和注入行为的影响；旧报告不能归因为它们。
- 实测 RTT/丢包率仍未实现，显示未知；策略丢弃量不是丢包率。

## 用户复验

关闭旧窗口、重启游戏，完整解压 candidate.2，进入联机菜单后连接。双接口成功应显示 hooks_ready3、state1/status0；开启并不在战斗、策略已确认时 effective_enabled1。若仍失败，保存新版诊断，优先检查 messages002.method/stage/slot/target/module/module_rva/win32_error/restore_error。无需上传原游戏或完整个人文件夹。

首次安装成功之后才验证一位已知黑名单玩家的搜索跳过/握手拒绝计数和是否进入确认。此版不声称 Steam 后端强踢或所有联机模式已成功。

最终 ZIP 的 SHA-256、字节数、CRC 和文件数由 downloads/0.1.0-candidate.2 清单及 Release 下载回验收据记录；旧 candidate.1 下载保留。

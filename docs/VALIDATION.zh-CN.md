# 0.1.0-candidate.1 验证范围

2026-10-07 UTC，沿用现有云环境。没有运行原游戏，没有连接真实 Steam 玩家。原生 Windows + 原版游戏匹配仍待用户验证。

## 已完成的检查

固定版本 MinHook 源文件 SHA-256 全部匹配。MinGW-w64 GCC 14，i686-w64-mingw32，静态运行库，PE32 GUI 与 DLL 构建通过；项目 C++ 编译启用 `-Wall -Wextra -Werror`。本机临时自建控制程序不进入 Git、源码 ZIP 或 Windows 包，按用户要求不发布测试集。

Wine 11.0 x86 / QEMU-i386 下：

| 范围 | 结果 | 证明内容 |
| --- | --- | --- |
| 自建进程中执行实际 runtime.cpp | 33 项通过，退出0 | 完整 SteamID 判断、场景1放行、GUI 心跳过期停止、非法 identity 放行、原结果/LastError 保留、有界候选压缩、全部拉黑归零、越界保持原数据、Join 原失败 flag、lobby 事件过滤与退出清理 |
| 旧 P2P 和新 Messages 接口控制 | 包含于上述33项 | 发送与接受拒绝、其他玩家放行；旧接收排空黑名单消息；现代收包压缩和准确释放一次 |
| 六个真实 PE32 自建函数的 MinHook detour | 包含于上述33项 | 真实 thiscall→fastcall→原 trampoline 路径、现代 receive hook、已有对战放行；不是只调用伪函数替代 hook 安装 |
| 实际 GUI EXE 的跨进程操作 | 14 项通过，退出0 | 创建窗口与控件、从空名单添加、UTF-8 文件落盘、关闭退出、重开恢复、选中移除及文件更新 |
| 最终候选 DLL 实际 LoadLibrary | 通过，退出0 | 导出可解析；空请求拒绝；自建非游戏宿主被版本检查拒绝，无 hook 安装 |

临时控制使用自建候选结构、接口、账号及消息，不代表读取到了游戏真实队列。现代 message 前缀按固定 SDK 的 packed identity 对齐检查，identity+12；释放对象调用路径按配套 DLL flat export 合同实现。

这次排查中，Wine 的同进程 WriteProcessMemory 返回拒绝，最终实现改为**DLL 内先验证可写范围再直接写对象**。单独 GUI 操作检查通过，但 Wine 截屏得到全黑画面；无法用其验收实际绘制、中文字体或 DPI 效果。原生 Windows 显示由用户确认，本文不将“窗口存在、控件可操作”描述为视觉验收通过。

## 尚未验证

- 注入真实 `uni2.exe`、真实 Steam 客户端接口 vtable 的 hook 安装。
- 游戏搜索生产回调中的真实 owner、room、index 生命周期与并发取消。
- 所有匹配模式是否均能在确认界面前拒绝黑名单玩家。
- 对方已进入 Steam 后端房间后，槽位与界面何时超时释放、下一位玩家何时能加入。
- 首次初始化接口到控制线程安装 hook 之间最多约100毫秒的窗口。
- 场景1检测在原版实战中的完整覆盖，以及与 uniGGPO 同时加载的兼容性。
- 原生 Windows 的字体、显示缩放、权限差异和安全软件对 DLL 注入的实际行为。
- 实测 RTT 和丢包率：本版未实现，明确显示未知；不会把策略拦截计数当作网络丢包。

接口未齐全、版本不匹配、入口签名变动或挂钩安装失败均明确报告，不宣称保护成功。磁盘 EXE 不修改。整个检查未启动原游戏，也未使用旧 Python 战斗模拟。

## 用户验证入口

先在联机菜单和新搜索前连接插件，再对当前候选添加名单。重点观察是否进入确认、原游戏是否继续搜索、等待房间是否被占用。窗口中的搜索次数、候选跳过和握手拒绝计数可判断实际命中了哪一层。“保存诊断状态”可提供不含玩家名单的本地状态文件。需要进一步逆向时，应根据该实际现象补充原取消/房间重建合同，不能用伪造失败回调替代。
